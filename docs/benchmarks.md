# Benchmarks

These are local, whole-command measurements of release falcon, `dart analyze`, DCM, and DCL, not a claim that the tools perform identical work. The same-rules family compares falcon with `dart analyze`; the DCM/DCL family uses its own shared ruleset. `dart analyze` additionally performs full Dart type analysis and reports compiler errors, warnings, and non-lint diagnostics. Falcon is not a replacement for that type checker.

The machine-readable results, individual wall-clock samples, exact commands, diagnostic distributions, source revisions, and dependency-resolution failures are published in [benchmarks.json](https://github.com/JacobDevelops/dart_falcon/blob/main/website/src/data/benchmarks.json). The [interactive benchmark page](https://dart-falcon.jacobdevelops.com/benchmarks) reads the same data.

## Reproduction

From the repository root on Linux, with Rust, mise, git, GNU time (`/usr/bin/time`), gzip, GNU base64, sha256sum, and network access available:

```sh
mise install hyperfine@2.0.0 flutter@3.47.7-stable
cargo xtask bench-compare
```

Run on an otherwise idle machine without concurrent builds, tests, or other substantial workloads. `makers bench_compare` is an equivalent task alias. Run `cargo xtask bench-compare --help` for overrides. The defaults are one warmup, three measured cold-cache runs, and five measured warm-cache runs per command. `--cold-runs`, `--runs`, and `--warmups` change those counts; `--skip-build` explicitly reuses an existing release binary. `--dart` must name the real SDK executable rather than a shim; `--hyperfine` overrides hyperfine's executable. Hyperfine 2.0.0 exports wall-clock samples; the published numbers are its mean, sample standard deviation, minimum, and maximum in milliseconds, not a best-of-run result. The same-rules family compares Falcon with `dart analyze` using the shared mapped official lint set.
 
The harness also runs a DCM/DCL family using a different ruleset: 39 DartCodeLinter-sourced candidate rules (the 42 declared rule IDs minus command IDs `check-unused-code`, `check-unused-files`, and `check-unnecessary-nullable`). The `--dcm` and `--dcl` executable overrides are optional; absent overrides, DCM is discovered at `$HOME/.local/share/dcm/1.40.0/dcm` and the DCL snapshot under the configured Pub cache. For DCM 1.40.0 Free, the harness uses a fixed shared set of 31 selected IDs: seven subscription-only candidate IDs and unavailable `use-design-system-item` are excluded. The exclusions and reasons are recorded in the report; unsupported IDs are not silently dropped. DCL 4.4.4 accepted the selected IDs without renames. Install DCM from the [1.40.0 Linux x64 release asset](https://github.com/CQLabs/homebrew-dcm/releases/download/1.40.0/dcm-linux-x64-release.zip), export the license securely as `DCM_LICENSE_KEY`, then activate with `DCM_EMAIL=<your DCM account email> dcm activate --license-key="$DCM_LICENSE_KEY"` (never put the license key in shell history or documentation). Install DCL into an isolated Pub cache with `PUB_CACHE="$HOME/.local/share/falcon-bench-pub" "$FLUTTER_ROOT/bin/cache/dart-sdk/bin/dart" pub global activate dart_code_linter`; its snapshot is at `$HOME/.local/share/falcon-bench-pub/global_packages/dart_code_linter/bin/metrics.dart-3.13.5.snapshot`. DCM Free's console reporter is parsed for rule IDs because Free does not provide JSON/checkstyle output; output rule IDs are cross-checked against summary totals and DCM rule links. The Free plan permits at most 50,000 analyzed lines. DCM is measured for dio and bloc; flame and flutter/packages plugins are explicitly unmeasured because each DCL-family source subset exceeds that limit. The full DCL-family inventory reports `dclFiles` and `dclLines`, the actual source subset after generated-file exclusions; those counts must agree across the three family tools. Reports list over-limit cases in `corpus.notMeasured` with the reason `exceeds DCM Free 50k-line limit`, and omit a DCM result row rather than presenting it as zero.

For example, run a bloc smoke comparison to a separate output file: `cargo xtask bench-compare --corpus bloc --dcm "$HOME/.local/share/dcm/1.40.0/dcm" --dcl "$HOME/.local/share/falcon-bench-pub/global_packages/dart_code_linter/bin/metrics.dart-3.13.5.snapshot" --output target/bench-smoke.json`. For a full default publishing run, install the tools as above and run `cargo xtask bench-compare` with no overrides. The smoke subset is not the full benchmark. Use a distinct `--output` path so it cannot replace the committed report; that report remains unchanged until a full, publishable run is produced and reviewed.

The harness builds `target/release/falcon` with Cargo's `--locked` flag, verifies Dart 3.13.5, fetches pinned source commits into the gitignored `target/bench-corpora/` directory, and runs `flutter pub get` during setup, outside the timed section. The release executable's SHA-256 is recorded alongside its reported version. Dependency setup is repeated to refresh SDK paths even when a package configuration already exists. Existing lockfiles are enforced rather than silently upgraded. Each corpus embeds all resolved `pubspec.lock` files in `dependencyLocksGzipBase64`: base64 of a gzip-compressed JSON object mapping relative lockfile paths to their complete content. A reproduction restores these snapshots from the committed results before running `pub get --enforce-lockfile`. This preserves registry versions, integrity hashes, and resolved git revisions without shipping large uncompressed lockfile copies to the website. An incomplete checkout or a changed pin is repaired by fetching and checking out the required revision inside the disposable cache.

Subpackages whose dependencies cannot resolve are excluded from **both** tools and the reported source counts; their paths and package-manager errors are retained in `corpora[].setupFailures`. A reproduction preserves these exclusions, removes cached lockfiles absent from the recorded snapshot, and aborts if another package stops resolving or the source counts change, rather than silently shrinking the workload. A previous report without lock snapshots cannot be used to reproduce dependency resolution. Workspace members use their workspace's dependency resolution. This is not a successful-build benchmark: analyzer compilation diagnostics on the remaining source are retained and counted.

The flutter/packages workload is a sparse checkout of the camera, google_maps_flutter, and webview_flutter package families, not the entire monorepo. The included directories are recorded in the report. The complete monorepo was rejected as unsuitable for this machine; no timing or memory number from that interrupted attempt is published.

Before each tool/scenario's timing batch, one separate untimed invocation captures diagnostics and GNU time's `%M` maximum resident set. `peakRssMb` converts its KiB value into decimal megabytes; this is the largest individual process resident set reported by GNU time, not summed allocations or a claim of peak aggregate memory. All tools and corpora run sequentially. A Linux `/proc` monitor samples the complete descendant process tree every 100 ms and recursively stops and kills that tree if aggregate RSS exceeds 8 GiB or a batch exceeds 15 minutes. Commands inherit the foreground process group so terminal Ctrl-C reaches the tools directly. The guard remains active during hyperfine; no memory-monitoring wrapper is placed inside the timed command. An over-limit or failed measurement stops publication instead of being counted as a fast result.

The same monitor rejects a pass if any benchmark process has nonzero Linux `VmSwap`. Host-wide swap-in and swap-out page-counter deltas are separately recorded as `swapPagesRead` and `swapPagesWritten`; these include unrelated desktop activity and are not presented as the tools' own I/O. Already occupied but inactive system swap is not a measurement of benchmark memory.

## What is timed

The same-rules family commands are `falcon check . --config <generated-config> --format json --exit-code 0` and `dart --suppress-analytics analyze --format=machine .`. The DCM/DCL family commands are `dcm analyze --no-analytics --no-global-version --sdk-path <sdk> --exclude '{**/*.g.dart,**/*.freezed.dart,**/*.mapper.dart}' .` and `dart <metrics.dart-3.13.5.snapshot> analyze --reporter=json --no-verbose --exclude '{**/*.g.dart,**/*.freezed.dart,**/*.mapper.dart}' .`, respectively. Both families use the same hidden-directory, dependency-cache, and build-directory exclusions. In addition, all three tools in the DCM/DCL family exclude generated files matching `**/*.g.dart`, `**/*.freezed.dart`, or `**/*.mapper.dart`; these family-specific exclusions are recorded in the report. DCM may intrinsically skip generated diagnostic files beyond these patterns, so identical filenames do not guarantee identical emitted diagnostics. Each family runs Falcon plus its comparison tools against its own generated rule configuration; no launcher, dependency download, or release build is timed. DCM license activation is required before measuring. Its personal Free license refuses CI unless the `CI` environment variable is unset for DCM only. The source files actually in the DCM/DCL-family workload are counted independently as `dclFiles` and `dclLines`; the three tools' counts must match. DCM's verbose footer can also count the `pubspec.yaml` it analyzes, so this comparison uses DCM's progress count of analyzed Dart files rather than that footer total. This avoids showing full-corpus counts for DCL-family charts when generated files are excluded.

For the same-rules family, all existing analysis-options files in the disposable checkout are replaced by one explicit corpus-root configuration; project-specific lint includes and settings do not influence the comparison. Falcon's recommended file and cross-file rule sets are disabled before enabling the corresponding mapped official rules. This deliberately enables conflicting style preferences too: it is a shared-rule exercise, not a recommended application configuration. No falcon-only rules are added. For the DCM/DCL family, the generated configuration enables only the 31 selected DartCodeLinter-sourced rule IDs. The common hidden-directory, dependency-cache, and build-directory exclusions apply to every tool. The DCM/DCL family additionally excludes generated files matching `**/*.g.dart`, `**/*.freezed.dart`, or `**/*.mapper.dart` from Falcon, DCL, and DCM; its `dclFiles` and `dclLines` inventory describes this actual source subset. Source files, including tests and checked-in generated Dart outside those patterns, remain in scope. Before timing, Falcon's public CLI file walker must discover exactly the reported Dart-file count with the generated configuration; a mismatch stops publication.

The rule declarations are the authoritative source of analyzer names (`RuleSource::Lints` in `crates/falcon_rules/src/lint/<group>.rs`; project-wide declarations are in `crates/falcon_rules/src/cross_file.rs`). The older headline of 142 official ports does not describe the full current mapping; the benchmark enables all 215 current mapped names. Undefined, removed, or replaced lint-name diagnostics cause the harness to stop rather than publish a silently different rule set.

The analyzer also reports six `INCOMPATIBLE_LINT` configuration warnings because this exhaustive set includes opposing style preferences. Those warnings do not remove either enabled rule: Dart 3.13.5's [options parser](https://github.com/dart-lang/sdk/blob/3.13.5/pkg/analyzer/lib/src/analysis_options/analysis_options_parser.dart#L153-L157) passes the configuration to the [rule registry](https://github.com/dart-lang/sdk/blob/3.13.5/pkg/analyzer/lib/src/lint/registry.dart#L117-L128), which selects every explicitly enabled lint. The warnings remain in the non-lint diagnostic counts.

## Cache scenarios

- **Cold analyzer cache:** `ANALYZER_STATE_LOCATION_OVERRIDE` points at a corpus-specific directory inside `target/bench-corpora/`. Hyperfine removes only that directory before every invocation, including warmups. The machine's real `~/.dartServer` directory is never cleared. The Linux filesystem page cache is not dropped, so “cold” does **not** mean a cold disk, SDK download, or dependency installation.
- **Warm analyzer cache:** the same isolated directory is retained across warmups and measured invocations. Every invocation still starts a fresh analyzer process; no analysis-server daemon is kept alive.
- Falcon has no persistent analysis cache on this command path. Its two scenarios use the same fresh-process command. Clearing the isolated analyzer directory is also applied before cold Falcon runs, outside timing, for symmetry.
- DCM and DCL use isolated per-corpus tool-state directories: DCM's `.dcm-teams-1390` and DCL's `.dart-code-linter`. Cold runs remove only the corresponding corpus-specific directory before invocation; warm runs retain it. Both locations were confirmed by tracing state-file writes.

The Dart analyzer's physical filesystem implementation documents `ANALYZER_STATE_LOCATION_OVERRIDE` as its state-directory override. After the measured run, the isolated analyzer directory contained `.analysis-driver/` entries, `.plugin_manager/`, `.instrumentation/`, and `.prompts/`; the analyzer actually used the overridden location.

## Interpretation and limits

Diagnostic counts are captured in a separate untimed invocation with the identical command and configuration. In the same-rules family, the report distinguishes `lintDiagnostics` for the enabled official names, `nonLintDiagnostics`, `errorDiagnostics`, and the total `diagnostics` count. In the DCM/DCL family, per-rule keys retain upstream DCL hyphenated rule IDs; they are not normalized to official analyzer lint names. DCL-family `errorDiagnostics` counts Falcon syntax errors and DCL/DCM rule issues at error severity; the latter can also be included in per-rule lint totals, so these fields may overlap. Totals are not discarded on a nonzero analyzer exit. Analyzer exit codes 0–3 are expected diagnostic outcomes; unexpected failures abort publication. Falcon is forced to exit zero for lint findings; a nonzero timed or capture-process Falcon exit aborts publication. Timing output and the separate diagnostic captures remain in the cache directory for inspection.

Equal enabled names within a family are not evidence of equal emitted diagnostics on arbitrary applications. Source exclusions, generated-code handling, suppressions, analyzer-only type checking, and rule implementations can affect output. The same-rules family compares identical enabled official lint names; the DCM/DCL family compares upstream DCL rule IDs across its tools. Results report observed differences rather than claiming corpus-wide diagnostic parity from a shared configuration. The project's focused parity fixtures and these public-project measurements answer different questions.

One verified difference is suppression syntax, not an extra rule: Falcon deliberately recognizes `falcon-ignore` directives rather than Dart's `ignore` / `ignore_for_file` comments. Bloc's `example/main.dart:1` suppresses `avoid_print` for the analyzer, while Falcon reports the unchanged `print` calls. Likewise, `lib/src/bloc.dart:83,182` suppresses `prefer_asserts_with_message`, and `lib/src/bloc_base.dart:32` suppresses `one_member_abstracts` only for the analyzer. These original comments are retained; the benchmark does not rewrite source to manufacture matching totals. This explains those observed discrepancies, not every possible difference between the two implementations.

These measurements are specific to this CPU, operating system, SDK, compiler build, and source revisions. CPU frequency, background load, filesystem caching, and dependency resolution can affect results. They are not a controlled comparison of asymptotic algorithms or an assertion that a linter can replace type checking. The DCM/DCL family uses 31 selected DartCodeLinter-sourced rules from 39 candidates rather than the shared official-lint set, and currently has no committed full-corpus measurement; a bloc-only smoke run is not representative. DCM requires an activated license, and DCM Free's console reporter limits diagnostic-capture formats. Immich's mobile project was considered but excluded because its exact Flutter 3.47.2 constraint does not match the required Flutter 3.47.7 / Dart 3.13.5 environment.

## Published measurements

The [benchmark page](https://dart-falcon.jacobdevelops.com/benchmarks) renders timing charts, result tables, diagnostic counts, and largest-process peak RSS directly from the committed JSON, immediately above this methodology. Those generated views, rather than hand-copied tables here, are the source of measured results. The JSON also records the measurement date, machine, tool versions, executable hash, and individual samples. `machine.cores` is the number of available logical threads, not physical CPU cores.

Published command and provenance paths use executable basenames and corpus-relative paths for portability; tool versions are bare version numbers. The actual timed invocations resolve the SDK and release executables to direct absolute paths before starting hyperfine; no launcher overhead is timed.

Cold and warm results must be considered together. An analyzer-to-Falcon time ratio above one favors Falcon; below one favors the analyzer. Cold analyzer state is relevant to fresh CI environments, but it does not represent every CI setup: persistent analyzer caches can change the result.

### Diagnostic differences

The shared configuration is reproducible, but **corpus-wide diagnostic parity was not observed**. The page and JSON retain each tool's actual counts, including parser/compiler errors and non-lint warnings:

- Bloc's extra lint findings correspond to the original Dart-only suppressions described above: `avoid_print`, `prefer_asserts_with_message`, and `one_member_abstracts`. The analyzer also reports incompatible-rule warnings.
- Checked-in generated Pigeon sources, such as `camera_android/lib/src/messages.g.dart:7` and `google_maps_flutter_android/lib/src/messages.g.dart:7`, contain `// ignore_for_file: type=lint`. Dart honors this suppression; Falcon's distinct suppression syntax does not. Thus both traverse the same source tree without emitting the same generated-source lint workload. This is a material limitation of an enabled-name comparison, not evidence of equivalent lint execution.
- The Flutter plugin families include shared helper sources without their own package manifest. For example, `google_maps_flutter_ios_shared_code/example/integration_test/google_maps_test.dart` cannot resolve `dart:ui`, `package:flutter/material.dart`, or its example application's imports in this standalone checkout. The analyzer retains these import/type errors and their downstream diagnostics; successful dependency setup does not mean these helper files form a buildable application. The plugin workload therefore must not be presented as a clean application-build or equal-diagnostic benchmark.
- Falcon reports parser diagnostics in `camera_web/example/integration_test/helpers/mocks.mocks.dart`, starting at line 274 on the record-type cast `as ({int? audioBitrate, int? videoBitrate})`. These are retained and counted, not hidden as successful parsing.
- Dio's generated `test/mock/http_mock.mocks.dart` explicitly suppresses `unnecessary_parenthesis` for Dart. Other observed differences include Dio's `require_trailing_commas` and `prefer_final_parameters`, and Flame's `avoid_print` and `cascade_invocations`. Suppression differences are verified, but the remaining per-rule differences have not all been attributed to individual source expressions. The full distributions are published rather than treating matching rule names as proof of exact parity.
- Flame's analyzer non-lint findings include incompatible-rule and deprecated-lint warnings. No configured name was unrecognized, removed, or replaced.

These measurements compare the commands a user runs, with their actual suppression behavior and type-analysis work. They are not an isolated measurement of equal amounts of lint-engine work.
